# Decisions

One line each: decision, then the reason.

- **CashScript/cashc 0.14.0, `pragma ^0.14.0`**: the latest stable release. It uses `this.age` instead of `tx.age` for relative timelocks, so the PRD's `tx.age` became `this.age` (same `OP_CHECKSEQUENCEVERIFY` semantics, no rule weakened).
- **`@bitauth/libauth@3.1.0-next.8`**: this is the version cashscript 0.14 itself depends on. Mixing it with 3.0.0 would duplicate types and VM.
- **Reclaim sets `nSequence = reclaimBlocks`**: CashScript's TransactionBuilder defaults to `0xfffffffe`, which fails CSV. The tx version is already 2.
- **`reclaimBlocks` limited to 1..65535**: keeps the CSV operand a pure block-based BIP68 lock (bit 22 and bit 31 clear), so a config can't accidentally become time-based or disabled.
- **The OP_RETURN hint is a single 57-byte push** (`6a 39 …`): this gives an exact, fixed byte layout. Multiple pushes would make the "exactly" in the spec ambiguous.
- **The contract address is P2SH32**: CashScript's default and the modern standard. P2SH20 has weaker collision resistance for covenants.
- **Workspace packages export TS source** (no per-package emit): Vite, tsx, vitest and ncc all consume TS directly, and `build` = compile contract + typecheck + bundle. This avoids build-order bugs.
- **`Chain` wraps `@electrum-cash/network` directly**, with ordered server fallback and a shared CashScript `ElectrumNetworkProvider`. CashScript's provider alone has no fallback and no `get_history`.
- **Chipnet servers: `chipnet.bch.ninja`, `chipnet.imaginary.cash`**: both probed live. `chipnet.c3-soft.com` refused WebSocket connections.
- **Mainnet explorer `explorer.bch.ninja`, chipnet explorer `chipnet.imaginary.cash`**: the chipnet one returned HTTP 200; the mainnet one is the matching operator's explorer.
- **The Action uses `runs.using: node24`**: GitHub deprecated the node20 runtime in 2026. The code itself runs on Node ≥ 20.
- **The Action reads `bond.json` through the GitHub API**, not a checkout: the workflow needs no `actions/checkout` and can't read a PR author's modified config.
- **Per-issue workflow `concurrency` group + hidden marker comments + fresh UTXO re-check**: three layers of idempotency, so a bond is never double-broadcast.
- **e2e uses a fresh registry address per run**, so each run's discovery scan is small and isolated from the repo registry. Discovery logic is identical.
- **e2e issue subjects are `bond-e2e/run-<time>#n`**, unique per run, so old runs can't make assertions pass.
- **Negative tests assert both** the CashScript VM evaluator (`.debug()`, which names the failing `require` line) **and** the node's rejection of the broadcast raw tx.
- **WizardConnect relays**: primary `wss://relay.riften.net:443` and fallback `wss://relay.cauldron.quest:443` (the documented defaults), overridable with `VITE_WIZ_RELAY_PRIMARY/FALLBACK`.
- **The wallet scan covers receive 0..19 and change 0..9** (derived locally from the xpubs WizardConnect shares). The contributor identity and refund address are receive/0.
- **`broadcast: false` in the WizardConnect request**: the app broadcasts itself, so the UI only shows success with a txid that Electrum accepted. Before broadcasting, it also checks that output 0 of the signed tx is the bond.
- **BCH WalletConnect v2 was not added**: WizardConnect is the required path. Adding a second wallet stack would cost more than the PRD's ~1-hour budget with no way to test it here.
- **The faucet script asks a human to solve the captcha** (it saves the PNG, then reads the sum from the TTY or `FAUCET_CAPTCHA`): tbch.googol.cash requires a captcha, and automated solving isn't appropriate.
- **`pnpm check:network` ignores comments, the `isTestnet` property name and the hackathon name "Mainnet Track"**. Those aren't network selectors; everything else must come from `network.ts`.
- **Timelock unit = 10 minutes (chipnet: 1 unit = 10 blocks, mainnet: 1 unit = 1 block, for now)**: chipnet runs Faster Blocks (CHIP-2025-03, ~1-minute blocks), which keeps legacy `nSequence`/BIP68 block locks on the old 10-minute scale. Evidence: the CHIP draft quoted in the thread says "the nSequence field for transaction inputs is interpreted under the same 10-minute assumption" ([thread](https://bitcoincashresearch.org/t/chip-2025-03-faster-blocks-for-bitcoin-cash/1513), post 5), and chipnet blocks measured at ~70 s average. The decisive data is a live test: a `reclaimBlocks = 1` spend was rejected `non-BIP68-final` by Bitcoin Cash Node 29.2.1 at 4, 5, 6, 8 and 9 confirmations and accepted at 11 (txid `63494ff71d0f2a42e4090a68764303651c23e4bf1e4d96d11a5c4c6d37668912`), and the full e2e run's reclaim was accepted on the first attempt at exactly 10 confirmations, so the threshold is `reclaimBlocks * 10` confirmations. A plain P2PKH spend with sequence 1 was rejected the same way, which shows the contract is not at fault. The contract is unchanged. The CHIP's exact rule and mainnet activation date could not be read from a primary spec (the BCHN 2026-05-15 upgrade spec doesn't cover it); mainnet stays at factor 1 until that is confirmed.
- **`relativeLockBlocksPerUnit` and `avgBlockSeconds` per network in `network.ts`**: status requires `confirmations >= reclaimBlocks * factor`, and the node is the final judge: `non-BIP68-final` shows "Not yet: try again in ~X minutes" in the web app, the Action and the CLI, and e2e test 4 retries every 60 s for up to 30 min.
- **Timeouts are shown in minutes, not blocks**: a lock unit is ~10 minutes on both networks, so a repo's `reclaimBlocks: 1` is ~10 minutes everywhere.
- **1-block safety margin on chipnet (`relativeLockSafetyBlocks`)**: the UI marks a bond reclaimable at `reclaimBlocks * 10 + 1` confirmations (11 for `reclaimBlocks: 1`). The node accepted at exactly 10 in the final e2e run, so the margin only guards against a judge clicking the button a block early; the node is still the final judge. Mainnet margin is 0.
- **Production web builds default to mainnet and ignore the local `.env` network**: the in-app "Practice on testnet" switch stores the choice in `localStorage` and reloads. Dev builds keep following `.env`.
- **The BLAZE banner is mandatory in code**: `vite build` fails unless all three `VITE_BLAZE_*` values are set (HTTPS URLs and a token-aware cashaddr), with a CI-only `BOND_SKIP_BANNER_CHECK=1` hatch. Empty values show a red TODO in dev, never an invented link.
- **USD figures come from Coinbase's public spot price, client-side, display only**: if it fails, the USD part is simply hidden. No user data is sent.
- **UI is a single dark theme, copy is short, pages are split into steps and tabs**; 3D (three.js lock) loads lazily and is skipped for reduced-motion users and browsers without WebGL. Fonts: Instrument Serif (hero), Bricolage Grotesque (titles), Space Grotesk (text), JetBrains Mono (numbers). Geist Pixel is not on Google Fonts, so it is not used.
- **Official logos**: only the Bitcoin Cash logo (from bitcoincash.org) is used as an image. CashScript, WizardConnect and Fulcrum appear as text names, because I could not verify an official logo asset for them.
- **UI theme follows hackathon.trycorpus.ai (requested)**: light grey page, white panels, black bands, green accent, Inter / Space Grotesk / Geist Mono, uppercase display headlines, mono top-bar links with a green underline, pill buttons, a live stats strip, numbered step cards, a dark flow band, rule-separated lists, a dark CTA block and a 4-column footer. Layout and tokens were read from their public stylesheet; **all copy, branding, logo and media are Bond's own**, and the ink animation is an original canvas (their hero video is not used). The earlier dark theme, 3D lock and curtain loader were removed in favour of the same slide-over intro that site uses (ink stage fills the screen, then the page slides up while the top bar slides down).
- **Logo: the approved linked-rings mark, used exactly as specified**. Two interlocked rounded links on a 64x64 box, stroke 7, no fill (left link `#EAF3EE` on dark or `#07100D` on light, right link BCH green `#0AC18E`). The left link is redrawn clipped to the top half so it passes over at the top crossing and under at the bottom. The wordmark "bond" is Space Grotesk Bold, letter-spacing -0.03em, converted to paths. The app icon is the dark mark at 81% on a `#07100D` rounded square. The brand folder did not exist in the repo, so every file in `packages/web/public/brand/` was generated exactly from the written spec (mark, light mark, mono mark, dark and light logos, icon, PNGs, favicon.ico). Logo SVGs use a tight vertical viewBox (44 tall) so they are usable at 22 to 32px; the geometry itself is untouched. Earlier exploratory marks (padlock, B monogram, b-with-coin, half-coin, a rough-filtered rings illustration) and the `design/` folder were removed. The loader's coin shows the official BCH logo on the front and the Bond mark on the back, then fades in the full logo; the hero art is the approved mark used as an image, with no filters.
- **BCH logo in the loader and on the 3D coin is the official symbol, unmodified**: the green circle and white B were extracted from `bitcoincash.org/img/bitcoin-cash-logo-wt.svg` without altering their geometry (`packages/web/src/lib/bchCoin.ts`). The loader draws a stroke along the same outlines for the "inking" effect, then fills; the geometry itself is never redrawn or distorted.
- **The reference has no 3D**: its ink is a video. The 3D scene is an addition requested in the brief, kept optional (lazy, paused off-screen, static fallback), so it can never break the page.
- **Ink hero is generated, not a video**: no media files to ship or license, and the canvas stays small and pauses off-screen.
- **Repo layout tidied**: one `README.md` at the root; `docs/` holds reference docs, `docs/proof/` the generated transaction list, `docs/submission/` the hackathon deliverables (deck, video script, report, original brief); unit and on-chain tests live together in `tests/`.
